# Pulse AI WhatsApp voice calling

Incoming WhatsApp calls use the existing Express webhook, Meta Graph signaling, and the LiveKit Cloud WhatsApp Connector. The server checks Meta's HMAC over the original HTTP body. MongoDB claims the Meta call ID and one concurrency slot. The connector negotiates SDP and dispatches the Node worker into a private WebRTC room. The worker uses the official LiveKit Google plugin and Google's Gemini Developer API for native, bidirectional audio. The default is the stable `gemini-3.8-live` model with the Kore voice. Gemini uses automatic language detection and voice activity detection, with interruption enabled. LiveKit handles WebRTC and sample-rate conversion. [Gemini 3.8 Live model](https://aistudio.google.com/docs/models/gemini-3.8-live) · [LiveKit Google plugin](https://docs.livekit.io/agents/models/realtime/gemini/)

Pulse AI loads the existing website knowledge and instruction set. Its typed tools reuse public catalog, booking validation, order quote and transaction logic, approved WhatsApp templates and Razorpay. The Google plugin converts the Zod tools to Gemini Live function declarations, and the server still validates every argument before execution. An explicit confirmation must match a final transcript from a new caller utterance. The worker uses local speech boundaries to associate each transcript with caller audio. Status lookups require a reference and the matching Indian phone number from the signed Meta call. A caller without a supported phone number, including a BSUID-only caller, can ask general questions and search products. Phone-dependent actions direct them to an existing verified channel. A callback creates an admin queue item for staff to handle outside the worker.

The worker disables LiveKit recording and transcription output. Transcription used for confirmations stays in memory. Call history stores identifiers, provider, model, usage counts and an optional broad topic only after the caller consents. Voice history expires after 30 days, including open callback requests. Existing order and repair records retain their own lifecycle. The dashboard estimates Gemini API cost from reported text, audio, tool-result and thinking tokens at published USD list prices. A cost appears only when Gemini supplies the modality breakdown. Provider billing, free-tier allowances, telephony and hosting are outside the estimate. Review each provider's data controls before enabling production. [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)

## Server configuration

Set secrets in the backend and voice worker environments. For local staging they can come from `server/.env`. Keep the same staging Mongo database, phone/WABA, model provider and LiveKit project on both processes.

- `MONGODB_URI` and existing backend settings, including `JWT_SECRET` for the web app.
- `WHATSAPP_ENABLED=true`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_BUSINESS_ACCOUNT_ID`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_WEBHOOK_VERIFY_TOKEN`, `META_APP_SECRET` and `META_GRAPH_API_VERSION=v26.0`. The voice connector can fall back to `META_ACCESS_TOKEN` if it has messaging permissions. The existing messaging flow still uses its own configured sender.
- `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` and optional `PULSE_VOICE_AGENT_NAME` (default `pulse-whatsapp-voice`). In LiveKit Cloud, open the project's Settings to find the WebSocket project URL and use its API keys page to create a server key and secret. [LiveKit Cloud](https://cloud.livekit.io/)
- `PULSE_VOICE_PROVIDER=gemini`, `GOOGLE_API_KEY` and `GEMINI_LIVE_MODEL=gemini-3.8-live`. In Google AI Studio, open **API Keys → Create API key**, select your staging project and paste the key into `GOOGLE_API_KEY` in `server/.env` or the server secret manager. The model name is a public identifier. The separate `GEMINI_API_KEY` setting continues to configure website and chat AI. The admin can select a supported model and voice for the server's selected provider. [Create or manage a Gemini API key](https://aistudio.google.com/app/apikey)
- For an optional OpenAI rollback, set `PULSE_VOICE_PROVIDER=openai`, supply `OPENAI_API_KEY` and optionally set `OPENAI_REALTIME_MODEL`. Restart both services with the same selection. Existing call history keeps its original provider. [OpenAI API keys](https://platform.openai.com/api-keys)
- `PULSE_VOICE_ENABLED=false` by default. Set it to `true` in staging when ready. The **Answer incoming calls** switch under **Admin → Manage WhatsApp → Voice calls** is separately off by default.
- `MAX_CALL_DURATION_SECONDS=600` and `MAX_CONCURRENT_CALLS=3` by default. The admin can set a lower limit for new calls.
- For online checkout, configure the existing Meta catalog, WhatsApp order payment template and Razorpay keys/webhook. For booking confirmations, use the configured, approved utility template. Confirm that the phone is listed as an active account in **Manage WhatsApp → Accounts**. [Existing WhatsApp checkout setup](whatsapp-checkout-setup.md)

## Meta Business configuration

1. In **WhatsApp Manager → Account tools → Phone numbers**, confirm the eligible Cloud API business phone and its WABA. The business must have a messaging limit of at least 2,000 unique recipients for production calling. A public test number or an eligible Tech Partner sandbox has relaxed testing prerequisites.
2. In the Meta app's **WhatsApp → Configuration / Webhooks** settings, configure or keep the existing public HTTPS callback at `https://<staging-backend>/api/whatsapp/webhook`. Use `WHATSAPP_WEBHOOK_VERIFY_TOKEN` for the challenge. Subscribe the app to the WABA or its associated Messaging account, and subscribe to both `messages` and `calls`. Verify the app has `whatsapp_business_messaging` for the number and the signing secret matches that app.
3. Select the gear next to the phone number, open **Calls**, enable incoming calling, and keep SIP and voicemail disabled. The Graph equivalent is an authenticated POST to `https://graph.facebook.com/v26.0/<PHONE_NUMBER_ID>/settings` with body `{"calling":{"status":"ENABLED","call_icon_visibility":"DEFAULT","sip":{"status":"DISABLED"},"voicemail":{"status":"DISABLED"}}}`. Read back via GET on the same path. Use call hours and icon controls if needed. Meta recommends opening the business chat info on the test phone to refresh the icon. This integration expects a sender token scoped to one Messaging account for the phone.
4. For staging messaging, verify `booking_confirmation` or the configured equivalent is approved with the correct language and booking-reference parameter. Verify the existing approved checkout template and catalog retailer IDs before trying online checkout. [Meta calling prerequisites](https://developers.facebook.com/documentation/business-messaging/whatsapp/calling) · [Meta call settings](https://developers.facebook.com/documentation/business-messaging/whatsapp/calling/call-settings) · [Meta webhook setup](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/create-webhook-endpoint)

## LiveKit and Gemini

1. Create or select a staging LiveKit Cloud project with WhatsApp Connector availability. In the project, obtain the WebSocket project URL and a server API key and secret. Configure the web service and agent with those variables. The web service calls the Connector API and dispatches by name, so the worker must register under the same name and project. The WhatsApp webhook continues to point at Express.
2. Select a Google AI Studio project with access to `gemini-3.8-live`. Confirm your project's usage and data settings. Google's free and paid tiers differ in how Google uses submitted data. Use synthetic customer details for the staging test.
3. Disable session recording in LiveKit Cloud and verify the project's observability and retention settings. Keep application logs structured and avoid forwarding provider payloads. [LiveKit WhatsApp Connector](https://docs.livekit.io/telephony/connectors/whatsapp/) · [LiveKit external agent hosting](https://docs.livekit.io/deploy/custom/deployments/) · [Gemini Live API](https://ai.google.dev/gemini-api/docs/live)

## Deployment and controlled test

1. Install with `npm ci` and `npm --prefix server ci`. Build the web app with `npm run build`. Keep the existing web deployment command, `npm --prefix server start`, and keep calling disabled in production.
2. In staging, start the web server and a separate always-on Node worker from the same revision with `npm --prefix server run start:voice`. Use a supported Linux glibc host. Allow outbound access to LiveKit Cloud, the Gemini Developer API, MongoDB and the shared business-service providers. Allow the worker to drain on shutdown. Configure staging secrets for test Razorpay and WhatsApp senders so the test uses staging orders and notifications.
3. Confirm the agent registered in the same LiveKit project, switch on the staging **Answer incoming calls** control, and enable the Meta calling setting for the test number. On an enrolled Android/iPhone, open the business chat info, place an inbound call and verify that one greeting plays. Speak in Hindi, English and Hinglish. Talk over a long answer and check that playback stops and the agent responds to the new turn.
4. Search inventory and check variant, stock and price against the staging catalog. Complete a repair and an online order only with explicit voice confirmation. Verify the confirmation/reference in MongoDB and the approved message in WhatsApp. Verify the online order stays pending until the test Razorpay payment webhook clears it. Try canceling before confirmation, a mismatched status reference, a template failure, and a callback that a staff user can resolve.
5. Place overlapping test calls, hang up during setup, and test the duration limit with a short staging cap. Check the dashboard provider, model, call state, duration, usage and estimated cost. Confirm a subsequent call can get a slot and LiveKit rooms close. Verify existing WhatsApp chat with a test message and check that no recording or transcript was stored. After testing, disable the staging phone setting and/or the admin switch as appropriate.

The automated tests mock Meta, the Gemini socket, the database and business tools. From the repo root run `node --test server/tests/whatsappGeminiLive.test.js server/tests/whatsappVoice.test.js` and `npm --prefix server test` for the backend suite. A successful controlled call is required before production enablement.
